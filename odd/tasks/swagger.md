# swagger

Objective: OpenAPI documentation for the NestJS API with Swagger UI, generated from the existing code (zod request schemas, response DTOs, guards and error filters).
Branch: `main` (user convention: work-unit commits directly on main, no PR). Delivery: commits per work unit. Test runner: none, by user decision (no tests in ODD features); checks are structural (`tsc`, build) plus runtime probes (dev server and built bundle).

## Specs

- **S1** — Swagger UI at `/api/docs` and the OpenAPI JSON beside it, built with `@nestjs/swagger` (12.x, compatible with Nest 12). The dependency is pinned to a release at least two weeks old.
- **S2** — Exposure (user choice): mounted only outside production. When `NODE_ENV` is `production`, `/api/docs` and the JSON answer `404` and no document is built.
- **S3** — Every endpoint is documented: auth, rooms, quotes and the six booking routes, grouped by tag. Each route lists its path parameters, request body, success response and the error statuses it can return (`400`, `401`, `403`, `404`, `409` with their `code` values from the booking HTTP contract in `odd/tasks/booking-flow.md`).
- **S4** — Schemas come from the code, with no second hand-written copy of request shapes: request bodies are derived from the existing zod schemas. Validation stays in `ZodValidationPipe`, so the `400` body (`statusCode`, `message`, `errors`) and every other runtime behavior stay unchanged. Response schemas are declared explicitly (the dev server runs through `tsx`, which emits no decorator type metadata, so nothing may rely on inferred types).
- **S5** — Session auth is described: routes behind `SessionGuard` declare the `lumni_session` cookie, and the UI can call them after signing in through the login route in the same browser.
- **S6** — Docs: README decision for the exposure rule (mirrored in `README.es.md`); API `CLAUDE.md` gains where the docs live and the rule that new endpoints document their body, responses and errors.
