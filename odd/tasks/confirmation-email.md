# confirmation-email

Objective: confirming a booking queues its confirmation email in the transactional outbox (D-07, D-09), and an in-process job triggered with `@nestjs/event-emitter` sends it once through Resend behind the `EmailSender` port (D-10). Retries are out of scope (a later ODD feature).
Branch: `main` (user convention). Delivery: commits per work unit, made only after the user approves them. Test runner: none, by user decision (no tests in ODD features); checks are structural (`tsc`, build) plus runtime probes. Prisma commands are run by the user.

## Specs

- **S1** — Scope (user request): implement a job driven by an event emitter in the booking confirmation endpoint (`POST /api/bookings/:id/confirm`) that sends the confirmation email with Resend.
- **S2** — Outbox kept (user decision, L2): the confirmation inserts one `email_outbox` row in the same transaction as the confirmation, with `UNIQUE(booking_id, type)` (D-07); the email (recipient, subject, body) is rendered once, at insert time, and stored in the row (D-09).
- **S3** — Job: after the confirmation commits, an in-process event is emitted; its listener sends the stored payload with the idempotency key `booking-confirmation/<booking_id>` (D-09) and records the outcome on the row: `sent` (provider message id, sent time) or `failed` (last error); each send increments `attempts`. Confirming never waits for the send.
- **S4** — No retries (user request): a failed email stays `failed`; no scheduler, backoff or re-processing in this feature.
- **S5** — `EmailSender` port with two adapters (D-10): Resend when `RESEND_API_KEY` is set, a local adapter (records the email without sending it) otherwise.
- **S6** — Docs: README D-08 and the stack table (+ `.es.md`), and the API `CLAUDE.md` ports list, updated to the event-emitter job. No tests (standing user rule).

Assumptions (marked so the user can correct them):
- *A1:* the table follows CONTEXT.md's `email_outbox` columns, including `next_attempt_at`, which stays null until the retry feature uses it.
- *A2:* the body is plain text; the sender is `EMAIL_FROM`, defaulting to Resend's test sender `Lumni Bookings <onboarding@resend.dev>`.
- *A3:* a repeated confirmation of an already confirmed booking queues nothing (D-06 returns it as is).
- *A4:* the admin outbox view of D-10 stays out of scope.
