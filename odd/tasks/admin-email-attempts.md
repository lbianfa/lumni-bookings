# admin-email-attempts

Objective: the admin booking detail in the SPA shows the confirmation email's indicator (status, recipient, last error) and its history of attempts, after the "Confirmation email" box of `AdminBookingDetail.dc.html`; the API records one row per send attempt and serves it to the admin only.
Branch: `main` (user convention). Delivery: commits per work unit, made only after the user approves them. Test runner: none, by user decision (no tests in ODD features); checks are structural (API `tsc` and build; SPA `tsc`, lint, build) plus runtime probes. Prisma commands are run by the user.

## Specs

- **S1** — Scope (user request): implement the indicator of the confirmation email's attempts in the booking detail, for the admin only, in the SPA.
- **S2** — Attempt history (user decision, L2): every send attempt is stored as its own row (when it happened, its outcome, the error if it failed), so the detail lists each attempt as in the design, not only the outbox's attempt count.
- **S3** — Admin only: the email and its attempts are served by an endpoint behind `SessionGuard` and `AdminGuard` (`401` without a session, `403` for a customer); the customer's booking responses and pages stay unchanged.
- **S4** — SPA: the admin detail (`/admin/bookings/<id>`) shows a "Confirmation email" box beside the booking, after the design: mail icon and title, a status badge, a summary line with the last error when it failed, and the list of attempts with their time and the wait since the previous one.
- **S5** — Docs: OpenAPI documents the new route (D-26); README decisions updated (+ `.es.md`); the API `CLAUDE.md` updated where it lists the `emails` feature. No tests (standing user rule).

Assumptions (marked so the user can correct them):
- *A1:* new table `EmailAttempt` (id, outbox email id with a restrict foreign key, `attemptedAt`, `outcome` `sent`/`failed`, `error`, `providerMessageId`); the job writes the attempt and the outbox row's outcome in one transaction. Outbox rows from before this feature (dev data only) are not backfilled: they show their status and count with an empty history.
- *A2:* the route is `GET /api/bookings/:id/email`; it answers `404` when the booking has no confirmation email (a draft, or a missing booking). The SPA hides the box in that case.
- *A3:* badge labels "Pending", "Sent", "Failed"; summaries "Waiting to be sent.", "Sent to <recipient> · <time>.", and for a failure "The attempt failed." or "All <n> attempts failed." followed by "Last error: <error>"; attempt times are `HH:mm:ss` in business time; the wait reads "after 30 s", "after 2 min".
- *A4:* while the email is pending the SPA reads it again every 5 seconds, so the box changes to sent or failed without a reload.
- *A5:* the stored email body (D-10's admin view of the content) and the cancel action of the design stay out of scope.
