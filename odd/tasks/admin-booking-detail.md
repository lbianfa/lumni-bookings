# admin-booking-detail

Objective: the admin's read endpoints for bookings (`GET /api/bookings` paginated and filtered, `GET /api/bookings/:id`) behind an admin-only guard, and an admin detail page that reuses the booking detail and reads from the new get endpoint. The bookings table is a later feature.
Branch: `main` (user convention). Delivery: commits per work unit, made only after the user approves them. Test runner: none, by user decision (no tests in ODD features); checks are structural (`tsc`, build, lint) plus runtime probes.

## Specs

- **S1** — Scope (user request): implement the admin view without the bookings table yet; reuse the booking detail page, which for the admin no longer reads from the `my-bookings` GET endpoints but from the bookings list and get endpoints this feature implements.
- **S2** — Access (user decision, L2): the admin reaches the detail only by its URL, `/admin/bookings/<id>`. The list endpoint is implemented and documented in the API only; the SPA does not consume it until the table feature.
- **S3** — Admin guard: both new routes require a valid session (`401` otherwise) and the `admin` role (`403` for any other user). *Assumption:* the role is read from the stored user on every request, as `SessionGuard` already verifies the session; the session cookie format stays unchanged.
- **S4** — `GET /api/bookings`: bookings of every customer, newest created first, filtered by optional `status` (`draft`, `confirmed`, `completed`, `cancelled`) and optional `roomId`, paginated by `page` (from 1). Invalid query values answer `400`. *Assumptions:* fixed page size of 10 (the design shows "Page 1 of 6"); the response is `{ items, page, pageSize, total, totalPages }`; each item is the My bookings item plus the customer's name (the design's "Customer" column); the design's "Email" column waits for the outbox feature (D-07..D-10), since no outbox exists yet.
- **S5** — `GET /api/bookings/:id`: any customer's booking with the same `BookingResponseDto` the customer reads; a missing booking answers `404`.
- **S6** — The customer's routes (`/api/my-bookings`, `/api/bookings` writes) and responses stay unchanged; the admin still cannot book (D-23).
- **S7** — SPA: `/admin/bookings/$bookingId` renders the existing booking detail (`BookingRecord`) from `GET /api/bookings/:id`, for a booking in any status, read-only (never the wizard). *Assumptions:* without the bookings list, the "My bookings" back link and the confirmation banner do not show; any other user opening an `/admin` route is redirected to `/` by an admin layout route (the router skill's RBAC pattern; revised from "not-found", L3); a missing booking shows the not-found state; no new nav link until the table exists.
- **S8** — Docs: OpenAPI documents both routes (D-26); a README decision records the admin reads and guard (+ `.es.md` mirrored); the API `CLAUDE.md` route notes updated if they list routes. No tests (standing user rule).
