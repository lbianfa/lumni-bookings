# booking-flow

Objective: the 3-step booking flow of CONTEXT §1.2 (`design/BookingStep1–3.dc.html`): draft started from the quote, customer details, room and schedule, services and an idempotent, concurrency-safe confirmation.
Branch: `main` (user convention: work-unit commits directly on main, no PR). Delivery: commits per work unit. Test runner: none, by user decision (no tests in ODD features); checks are structural (`tsc`, build, lint) plus manual probes (curl, browser).

## Specs

- **S1** — Scope: only the three steps, plus the "Start booking" action on the quote page that creates the draft (user choice). The "My bookings" page, the admin view and the confirmation email outbox (D-07–D-10) stay out; a draft is resumed by opening its booking URL again.
- **S2** — Module layout (user choice): `bookings` keeps full layers and the HTTP endpoints. Its parts live in their own internal modules, each without `http` or controllers, exporting only their repository: `customers`, `services`, `booking-lines`, `booking-services`. Confirmation shares one database transaction across those repositories through a unit-of-work port (`shared`), bound to a Prisma adapter running `db.transaction`.
- **S3** — Customer (user choice, recorded as a new README decision): one customer per user through `users.customer_id`. Step 1 is prefilled from that customer and saving it updates the customer; the booking references it. Changing the email to one another customer already uses returns `409`. The seed creates the customer of `customer@lumni.test`. *Assumption:* the admin user has no customer, so the booking endpoints answer `403` to it.
- **S4** — Booking reference (user choice): shown as `BK-{uuid}` built from the booking id; no extra column.
- **S5** — Data: `bookings` gains `customer_id`, `total`, `quoted_at`, `current_step`, `cancellation_reason`, `confirmed_at`, `cancelled_at`; new tables `customers`, `services` (seeded: projector COP 30,000, coffee service COP 25,000, D-14), `booking_lines` (`concept`, `amount`: base, discount, surcharge, each service) and `booking_services`. The D-05 exclusion constraint must survive the new migration. *Assumption:* `payment_status` is left out (Part 3 alignment only, no payment flow).
- **S6** — Draft lifecycle: "Start booking" creates a `draft` from an available quote, priced and stamped with `quoted_at`. Each step saves the draft and advances `current_step` to the furthest step reached, so reopening the booking resumes there. Step 2 changes are checked and priced again with the quote rules (§1.1, D-21); a slot that is not available cannot be saved. Step 3 stores the selected services; the total follows D-15. Only `draft` bookings can be edited. *Assumption:* the same availability rules apply when saving step 2 as when quoting.
- **S7** — Confirmation: `draft → confirmed` validated in the backend by a domain state machine with the guide's transition table (`draft → confirmed`, `confirmed → completed`, `confirmed → cancelled`; any other transition is rejected). Confirm runs the D-18 price rule, freezes the breakdown in `booking_lines` and sets `confirmed_at` in one transaction with the conditional update `WHERE status = 'draft'` (D-06). A repeated confirm returns the confirmed booking without recalculating; a slot taken by another confirmed booking (exclusion constraint, D-05) returns `409`.
- **S8** — Access: a customer can only read and edit their own bookings; another customer's booking returns `404`.
- **S9** — SPA: the three steps follow the designs (stepper, "Draft saved", quote summary, room and schedule with the price panel, services with the summary and the confirm button). Page selections live in component state, not search params; the booking id is the route parameter. *Assumption:* after confirming, the page shows the booking as confirmed and read-only.
- **S10** — No tests in this feature (standing user rule). Prisma commands (contract emit, migration plan/apply, seed) are run by the user; the agent hands over the exact commands.

HTTP contract (shared by W2 and W3). Every route needs the session cookie (`401` without it).

| Method and path | Body | Answer |
|---|---|---|
| `POST /api/bookings` | `{ roomId, date: "YYYY-MM-DD", startTime: "HH:mm", durationMinutes }` | `201` booking |
| `GET /api/bookings/:id` | — | `200` booking |
| `PUT /api/bookings/:id/customer` | `{ fullName, email, company: string \| null }` | `200` booking |
| `PUT /api/bookings/:id/schedule` | same as `POST /api/bookings` | `200` booking |
| `PUT /api/bookings/:id/services` | `{ serviceIds: string[] }` | `200` booking |
| `POST /api/bookings/:id/confirm` | — | `200` booking |

Booking body: `{ id, reference: "BK-<id>", status, currentStep: 1 | 2 | 3, customer: { fullName, email, company }, room: { id, name, size, hourlyRate }, date, startTime, endTime, durationMinutes, startsAt, endsAt, price: { base, discountPercent, discount, surchargePercent, surcharge, services: [{ code, name, price }], total }, services: [{ id, code, name, price, selected }], quotedAt, confirmedAt }`. Amounts are decimal strings with two places, as in the quote (`discount` and `surcharge` positive). Errors: `{ statusCode, message }`; `400` invalid body (with `errors`), unknown service or invalid slot; `403` the user has no customer; `404` booking (or another customer's booking) or room not found; `409` with a `code`: `slot_unavailable` (plus `reason`, the quote's reason code), `slot_taken` (another confirmed booking won the slot), `email_taken`, `not_editable` (not a draft), `step_not_reached`, `quote_expired` (D-18).
